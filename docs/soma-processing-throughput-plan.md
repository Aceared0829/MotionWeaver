# SOMA 批处理吞吐与续跑校验改造方案

状态：待实施。本文记录 2026-10-18 全库批处理中断后的实测结论与改造计划，尚未修改代码、尚未验证等价性。

## 1. 问题来源

批次 `20261018-soma-full-v1` 处理 `seed_metadata_v004.csv` 中 `is_mirror=False` 的 71,132 条、62,301,201 帧。2026-10-18 09:17 进程中断于 52,939 条，13:09 以 `--resume` 续跑。续跑前重新计算全部已写数据的 SHA256，耗时约 4 小时 10 分（13:09–17:20），占本轮总耗时三分之一以上。校验完成后实测处理吞吐约 113–133 条/分钟（2.1 条/秒），全批预计 9 小时以上。

E 盘为 USB 外接机械盘（`Generic External`，2.73 TB，UAS 连接），实测顺序写 19–23.5 MB/s、单次写延迟约 16.3 ms。输出约 71 万个小文件、预估 680–710 GB。

## 2. 实测结论

| 指标 | 实测值 | 说明 |
| --- | --- | --- |
| 8 个 worker 合计 CPU | 0.93 核 / 32 逻辑核 | 计算不是瓶颈 |
| E 盘写入吞吐 | 19–23.5 MB/s | 随并发数变化 |
| 单次写延迟 | 16.3 ms | 机械盘固有，不随并发改善 |
| 磁盘队列长度 | 1–4 | UAS 支持命令队列，尚未打满 |
| 已写数据量（52,939 条） | 约 509 GB | 11,401 B/帧 × 44,635,795 帧 |
| 全批输出预估 | 约 680–710 GB | 同上比例推算 |

吞吐关系为 `并发数 × 单次 IO 大小 ÷ 延迟`。延迟由硬件决定，单次 IO 大小由数据格式决定，**唯一可调变量是并发数**。

D 盘为 NVMe SSD，2026-10-18 可用 689.6 GB，小于全批输出量，只能用于分批周转。

## 3. 改造项

### 3.1 workers 上限（优先级最高）

当前实现硬限制 `1 <= workers <= 8`（`data/tools/process_soma_dataset.py` 的 `run()`）。CPU 侧余量充足，放宽上限可直接提升 E 盘写入并发。

计划：上限改为 `min(os.cpu_count() or 4, 32)`，并保留每 worker 内存占用检查。具体最优值由基准测试标定，不预设。

风险：机械盘寻道竞争可能使并发超过某点后收益反转，因此必须先测后定。

### 3.2 续跑校验分层

当前续跑对每条已完成回执的 `raw`、`processed`、`processing_arrays`、`observation` 全部重新计算 SHA256，并在主进程中串行执行（`ProcessPoolExecutor` 启动之前）。

计划新增 `--verify` 参数：

| 层级 | 手段 | 成本 | 用途 |
| --- | --- | --- | --- |
| `metadata`（默认） | 比较文件 `size` 与 `mtime_ns` | 毫秒级/条，全批分钟级 | 常规续跑 |
| `sample` | metadata 全查 + 1% 随机全量哈希 | 分钟级 | 定期抽检 |
| `full` | 逐字节 SHA256（当前行为） | 约 4 小时 | 归档前、怀疑损坏时 |

回执新增 `raw_stat`、`processed_stat`、`observation_stat`、`processing_arrays_stat` 字段，写入时顺带 `stat()`，不改变任何输出数据。既有回执可在跑完后一次性回填，只读取元数据，不需要读文件内容。

`metadata` 层漏过的情形仅限“大小相同且时间戳未被改动”的静默损坏，不属于 USB 机械盘的典型故障模式；`full` 层继续保留给归档场景。

### 3.3 journal 读取容错

当前 `run()` 逐行 `json.loads(journal)`，未处理解析失败。进程若在追加回执中途被杀，文件尾部会留下半截 JSON，下次续跑直接抛异常终止，而不是跳过该条重做。

计划：捕获 `json.JSONDecodeError` 后跳过该行，对应条目按未完成处理。

### 3.4 输出根分离（条件性）

仅在基准测试证明“顺序大文件拷贝显著快于当前多进程小文件交错写”时实施。若顺序写同样受 20 MB/s 限制，该方案无收益，直接放弃。

若实施，改造点为：`run()` 与 `process_clip()` 接受独立的输入根与输出根；回执同时记录最终路径（E 盘）与暂存路径（SSD）；所有索引使用最终路径；新增分批迁移阶段（写完一批 → 校验 → 搬到 E 盘 → 清理暂存），D 盘周转需求约 100 GB。

该项涉及路径语义变更，风险高于前三项，需单独等价验证。

## 4. 基准测试（实施前必做）

| 测试 | 方法 | 决定 |
| --- | --- | --- |
| A. 并发标定 | 用已完成数据做写入测试，workers 取 8/16/24/32 | 新上限取值；是否需要 3.4 |
| B. 顺序拷贝 | 将约 20 GB 既有输出复制到 E 盘另一目录 | 3.4 是否成立 |
| C. 单文件顺序写 | 向 E 盘写 1 GB 单文件 | E 盘顺序写上限 |

三项测试使用独立临时目录，结束后清理，不改动既有批次输出。

## 5. 验证流程

沿用仓库既有等价验证方式（参见 `docs/experiments/2026-10-18-soma-processing-speed.md`）：

1. 用 32 条小样本分别运行新旧版本
2. 逐字节对比 `raw/`、`processed/`、候选 NPZ 与 observation
3. 生成等价回执，含原 manifest SHA256、新代码 SHA256 与 `equivalent_outputs: true`
4. 以 `--upgrade-receipt` 续跑，原 manifest 自动归档到 `manifest-history/`

3.2 与 3.3 只增加校验逻辑与 `stat` 字段，输出数据不变，等价性可直接证明。3.1 改变并发执行顺序，但每条输出与顺序无关，需确认回执内容一致。3.4 需完整路径与哈希验证。

## 6. 执行顺序

1. 等待 `20261018-soma-full-v1` 完成（`progress.json` 为 `complete`），确认 `run.json` 与 `unresolved.json`
2. 执行第 4 节三项基准测试
3. 按测试结果确定 3.1 的上限取值，决定 3.4 是否实施
4. 实现 3.1、3.2、3.3 并完成等价验证
5. 回填既有回执的 `stat` 字段
6. 若 3.4 成立则单独实施并验证

**在批次运行期间不得修改上述代码。** `verify_resume_manifest` 会比对 `manifest.json` 中的代码 SHA256，任何改动都会导致续写被拒绝。
