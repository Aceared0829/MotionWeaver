# Tokenizer 码本塌缩：诊断与修复方案

## 一、诊断结论

**根因是码本超参组合不当，不是训练机制问题。**

逐层方差追踪（BC120，64 帧）证明信息在量化器一处塌缩：

| 层 | 形状 | 方差 | 相对输入 |
|---|---|---|---|
| x 输入 | (1, 64, 941) | 1.4201 | 100% |
| 特征抽取 | (1, 700, 64) | 1.9019 | 133.9% |
| **编码器输出** | (1, 256, 8) | **2.2850** | **160.9%** |
| **量化后** | (1, 256, 8) | **0.0291** | **2.05%** |
| 解码器输出 | (1, 941, 64) | 0.6167 | 43.4% |

编码器保留了全部信息（方差比输入还大 61%），量化后只剩 1.3%——**79 倍塌缩**。
解码器把 0.029 扩回 0.617，说明解码器本身工作正常。

三项配套证据：

- `perplexity = 5.64 / 10`（每 head 10 个码字只用 5.6 个）
- `l_commit_pose = 0.0050`（编码器几乎不推送码本）
- `ric_data` 残差 0.99（231 维相对位置几乎完全没编码）

## 二、已排除的可能（都实测过）

| 假设 | 验证 | 结论 |
|---|---|---|
| 梯度断裂 | 20 步真实训练，grad_norm 8.10→0.26 | ❌ 正常 |
| 优化器不更新 | decoder 权重 20 步变化 0.049→0.299 | ❌ 正常 |
| checkpoint 加载错 | strict=True 无报错，130 张量可训练 | ❌ 正常 |
| external_cond 没注入 | 维度契约满足；换随机数产生 0.135 差异 | ❌ 正常 |
| 容量不足 | 1 token vs 16 token，误差差 0.1% | ❌ 与容量无关 |
| 重尾分布 | 均值/中位 = 0.96× | ❌ 不重尾 |

**注**：此前「解码器退化成常量函数」的判断是错的——那是单样本内方差（43.4%），
正确的跨样本区分度是 21.3%，模型对输入是敏感的。

## 三、根因：`threshold_ema_dead_code = 1` 与 `decay = 0.99` 冲突

配置（`quantize_cnn_multihead.py:27-28`）：

```python
threshold_ema_dead_code = 1,   # 官方默认 0（禁用）
decay = self.mu,               # 配置 quantizer_mu = 0.99，官方默认 0.8
```

`vector_quantize_pytorch` 的语义：

- `threshold_ema_dead_code=1`：**某码字累计使用次数 < 1 就重置**为中心点
- `decay=0.99`：EMA 更新 `center ← 0.99×center + 0.01×batch_mean`，几乎不动

两者叠加会形成死循环：

1. 码字 A 被选用一次
2. 计数在 EMA 衰减下迅速回落到 1 以下
3. 触发重置，A 变成「当前 batch 的中心」
4. 由于 decay=0.99，新中心几乎不动
5. 下次又几乎不用它 → 回到第 2 步

结果是码字留不住、全部挤在中心附近——正是量化后方差只剩 1.3% 的机制。

## 四、修复方案

### 方案对比

| 方案 | 改动 | 参数量影响 | 风险 | 预期效果 |
|---|---|---|---|---|
| **P0 关掉死码重置** | `threshold_ema_dead_code: 0` | 0 | **最低** | 码字能稳定留存 |
| **P0 放缓 EMA** | `quantizer_mu: 0.99 → 0.9` | 0 | 低 | 码本更快适应数据 |
| **P1 增大 per_head** | `nb_code: 1e8 → per_head 32` | **+0.016%** | 低 | 组合空间 10⁸→32⁸ |
| **P2 提高 commit 权重** | `commit_loss_coeff: 0.02 → 0.1` | 0 | 中 | 编码器更贴近码本 |
| P3 启用 kmeans 初始化 | `kmeans_init: true` | 0 | 中 | 已 A/B 验证无优势 |

### 推荐方案：P0 两项一起改，其余不动

**理由**：P0 两项直接解除「重置/EMA 冲突」这个已确认的机制冲突，且零参数量变化、
零风险。P1 收益确定但需要重训验证；P2/P3 已被 A/B 或分析否定。

具体改动（`training/configs/pretrain/motionweaver_vqvae.yaml`）：

```yaml
quantizer_mu: 0.9        # 原 0.99；EMA 更快适应
```
```python
# quantize_cnn_multihead.py:27
threshold_ema_dead_code = 0,   # 原 1；关闭死码重置
```

**不改 `nb_code`**：它与 `num_heads=8` 共同决定 `nb_code_per_head`，
改它会连带改变码本结构，应作为第二步单独验证。

### 验证方式

重训 3 epoch（约 30 分钟），检查四项：

| 指标 | 修复前 | 期望 |
|---|---|---|
| `perplexity_pose` | 5.64 / 10 | **> 8** |
| `l_commit_pose` | 0.0050 | 回到 0.01-0.1 量级 |
| **量化后方差 / 输入方差** | **2.05%** | **> 20%** |
| 关节 RMSE | 105 cm | **显著下降** |

**量化后方差是最关键的判据**——它直接测「码字是否还携带信息」，
比 perplexity 更本质。

## 五、执行顺序

1. 改 P0 两处（1 分钟）
2. 用 `--max_steps 3000` 短跑验证量化方差是否回升（约 5 分钟）
3. 若回升 → 跑满 3 epoch（30 分钟）→ 全量 benchmark
4. 若未回升 → 说明还有别的因素，转查 P1/P2
