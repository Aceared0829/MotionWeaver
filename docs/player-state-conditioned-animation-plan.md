## 一、目标与不可丢失的边界

玩家给出移动意图和 `Stand/Crouch` 请求后，模型连续生成包括**蹲下、蹲伏移动、起身**在内的全身动画姿态。模型接收已显示的姿态历史，并能在过渡中响应方向变化、停步和反向状态请求。长期再扩展 Jump、Traversal、交互动作和更多姿态状态。

世界位移来源由用户选择 **Model Root、CMC 或 Mover**，三者是平行的运行模式，而不是用 CMC/Mover 永久取代 MotionBricks 原有 Root 预测器。任一时刻只能有一个执行者决定 Actor/胶囊体实际 Root；姿态生成器以该模式的短时计划 Root、已执行 Root、历史姿态及请求/获准站蹲状态为条件，生成 Root 相对身体姿态。起身请求被碰撞拒绝时，动画目标必须继续是可执行的蹲伏状态。`pose_only_root_authoritative` 仅描述 CMC/Mover 执行模式，不能概括 Model Root 模式。

| 可选世界位移模式 | 短时 Root 计划来源 | 世界位移与碰撞执行 | 联机风险与现状 |
| --- | --- | --- | --- |
| Model Root | 保留并发展原版 MotionBricks 的 Root 预测器；受玩家意图、历史和状态条件控制 | 专门的模型 Root 执行适配器，必须处理碰撞、净空与实际轨迹回写；不能只改 Mesh 根骨 | 自定义服务端权威、客户端预测与校正路径尚未实现；原版 G1 演示不能当作 UE 联机证据 |
| CMC | 从 CharacterMovementComponent 的当前状态与输入构建在线短时计划，训练要覆盖计划与实际 Root 偏差 | CMC 执行角色运动、胶囊体碰撞和其对应的网络移动路径 | 具体 Character 子类、预测状态编码和站蹲批准时序仍须在 UE 验证 |
| Mover | 从 Mover 的模拟状态与玩家输入构建在线短时计划，训练要覆盖模拟与执行差异 | Mover 的选定运动模式执行世界位移与碰撞 | Mover API、同步与回滚路径需按项目实际 UE 版本核验，不假定与 CMC 可直接互换 |

这三种模式共享姿态侧输入/输出契约，但不共享未经验证的移动实现。选择模式是用户/项目配置；切换模式时必须清空或迁移历史、计划和网络预测状态，禁止同帧双重施加世界位移。用户确认验收顺序为**先单机、随后监听服务器**；最大玩家数与 GAS 使用尚待确认。项目当前没有 `.agents/ue-project-context.md`，不能把尚未确定的网络细节当作已实现契约。

最终成功的含义是：**玩家意图能在连续游戏过程中及时改变合理的动画姿态，Root、胶囊体、脚部接触与画面一致，UE 中实测性能达标。**单窗口的离线姿态误差、指定参考帧的零误差或编辑器预览截图均不单独构成完成证据。

## 三、拟定的 v2 在线契约

先覆盖 Stand 与 Crouch，不急于把所有动作塞进一个大枚举。下表为**待实现设计**，形状与频率以 v1 的 30 Hz、24+24 帧为初始候选，须由延迟和动作时长实验确定。

| 字段 | 含义与来源 | 必须注意 |
| --- | --- | --- |
| `history_pose/history_rotations/history_root` | 最近连续显示的身体与权威 Root；启动时可用有效初始姿态填满历史。 | 闭环推理时使用模型已显示的结果，不能不断读取未来源动画。 |
| `requested_stance` | 玩家本次请求：Stand 或 Crouch。 | 输入事件本身不能证明碰撞准许或动画已经到位。 |
| `accepted_stance`、`can_uncrouch` | 当前位移执行者对胶囊体与头顶空间的实际结果；Model Root 模式也必须经过自己的碰撞/净空执行适配器，不能让模型自称已经获准。 | 起身受阻时不可向模型发送“必定站起”的目标。 |
| `locomotion_intent` | 期望局部移动方向、速度、朝向、步态及可选风格。 | 状态与步态分开表示；蹲伏行走和原地蹲伏都能表达。 |
| `root_mode`、`future_root_plan`、`executed_root` | 模式选择及其提供的短时 Root 计划与已执行轨迹；Model Root 来自原 Root 预测器，CMC/Mover 来自对应运动系统。 | 原动作未来 Root 只用于理想上界；线上不得取得真值。计划、碰撞截断和实际 Root 要分开记录。 |
| `timed_reference`（可选） | 可执行的目标姿态、落脚或交互关键帧及到达时间。 | 普通站蹲切换必须有无参考能力；测试参考不能从待预测的真值偷取。 |
| 输出姿态 | Root 相对的未来全身姿态；可附脚接触概率、过渡进度和有效性信息。 | 需要恢复 UE 层级局部变换，并补齐当前预览中依赖源动画的辅助骨骼。权威 Root 始终由当前选定的世界位移执行者提供。 |

`requested_stance`、物理上已获准的 `accepted_stance` 和从历史姿态观察到的视觉过渡进度是不同变量。状态机只管理请求、合法转换、碰撞和网络同步；它不代替模型播放一段固定的蹲下/起身动画。可选目标姿态库可像 G1 演示那样提供目标，模型仍须生成从当前动作到目标的合理中间帧。

**退出条件：**连续序列的状态响应、脚部、接缝和 Root 对齐通过人工与数值复核；所有失败和回退有计数与可复现日志。

- [ ] 先在单机真实角色/关卡中分别验证空旷地面、低矮障碍、斜坡和不同帧率；再用监听服务器与客户端验证所选模式的服务端权威、客户端预测、状态同步与校正后姿态收敛。尤其不能把 CMC/Mover 的现成网络路径推断成 Model Root 模式已可联机；多人规模待确定。

**退出条件：**新条件权重在 UE 玩家控制中实际运行，双向站蹲和打断场景通过；数值对齐、渲染观感、碰撞、推理预算和连续运行报告齐全。

## 六、遇到问题时的决策规则

1. **站蹲样本不够或标签不可靠：**先补独立数据与人工复核；不要靠无限重复现有 3 条训练过渡来“解决”。
2. **理想 Root 好、真实控制 Root 差：**先查轨迹预测、控制契约及训练/推理条件一致性，再判断是否需要改模型。
3. **离线误差好、UE 画面差：**按 Root↔Pelvis、坐标与参考轴、层级骨骼、蒙皮、脚接触、碰撞的顺序定位；保留实际截图与日志。
4. **硬参考到位、过渡不顺：**检查历史接缝、参考时刻分布、连续重规划及脚相位；不要只增加锚点覆盖强度。
5. **新模型超出帧预算：**先看执行后端和 CPU/GPU 拆分、固定形状、调用频率和缓冲，再考虑蒸馏或轻量结构；任何降频都必须重新测输入响应。
6. **试验收益互有取舍：**报告各场景收益与代价，保留无参考、固定参考、非固定参考以及站蹲过渡的分项结果；不以一个平均分替代选择。
